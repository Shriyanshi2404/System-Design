Abstract Factory Design Pattern

Problem Statement:
When an application needs to create families of related objects without specifying their concrete classes, and when you want to ensure that the created objects work together consistently.

Solution:
The Abstract Factory Pattern provides an interface for creating families of related or dependent objects without specifying their concrete classes. It's often called a "factory of factories" or "super factory."

Key Parts:
1. Abstract Factory (VehicleFactory):
   - Declares interface for creating abstract products
   - Contains abstract methods for product creation

2. Concrete Factories (LuxuryVehicleFactory, CompactVehicleFactory):
   - Implement operations to create concrete products
   - Each factory type creates a family of products

3. Abstract Products (Vehicle):
   - Declares interface for a type of product object

4. Concrete Products (Mercedes, BMW, Swift, Nano):
   - Implements the Abstract Product interface
   - Created by corresponding Concrete Factory

5. Factory Creator (FactoryOfVehicles):
   - Provides a way to get the appropriate factory

Implementation Example in Our Project:
1. Abstract Factory (VehicleFactory):
   - Methods: getLuxuryVehicle(), getCompactVehicle()

2. Concrete Factories:
   - LuxuryVehicleFactory: Creates Mercedes and BMW
   - CompactVehicleFactory: Creates Swift and Nano

Usage Example:
VehicleFactory factory = FactoryOfVehicles.getVehicleFactory("Luxury");
Vehicle luxuryCar = factory.getLuxuryVehicle();  // Creates Mercedes
Vehicle compactCar = factory.getCompactVehicle(); // Creates BMW

Benefits:
1. Isolation: Concrete classes are isolated from client
2. Consistency: Products from the same factory are compatible
3. Easy Product Family Change: Switch entire product family by changing factory
4. Single Responsibility: Product creation logic is centralized
5. Open/Closed: New variants can be added without breaking existing code

When to Use:
1. The System needs to be independent of product creation and composition
2. The System needs to be configured with multiple families of products
3. Family of related products is designed to be used together
4. You want to provide a class library of products while hiding implementation

Real-world Applications:
1. UI Toolkits: Different look and feel for different operating systems
2. Cross-platform Applications: Creating components compatible with different platforms
3. Vehicle Manufacturing: Different vehicle types for different markets
4. Document Generation: Creating different types of documents with consistent formatting

Design Considerations:
1. Factories should be singletons if possible
2. Consider using reflection or configuration files for factory creation
3. Plan for product family extensions
4. Consider providing default implementations for some products
